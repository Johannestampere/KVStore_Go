# Local benchmark — October 8, 2026

Six short runs exercised the benchmark CLI against a persistent five-node
cluster. All 30,000 measured requests and 6,000 preload writes succeeded,
including three runs with one replica stopped.

These are local development measurements, not a claim about production capacity.
The client and all node processes shared one machine and disk. Background host
load was not controlled, and the experiment did not sweep concurrency to find
saturation or measure sustained performance.

## Environment and workload

- Apple M5 Pro, 24 GiB RAM; macOS 26.6.2; Go 1.27.1, darwin/arm64.
- Native node processes on loopback, built without race instrumentation.
- Five static members, 64 virtual positions per node, N=3, R=2, W=2.
- Separate temporary append-only storage directory per node, with `File.Sync`
  before acknowledging durable mutations. No memory-only storage mode.
- Server deadlines: 2s per peer request and 5s per coordinated operation.
- Per run: 5,000 measured requests, concurrency 20, exactly 2,500 GETs and
  2,500 PUTs, 1,000 preloaded read keys, 256-byte ASCII values, 5s client timeout.
- GETs verified preloaded values; PUTs used unique keys in a separate namespace.
- Preparation was excluded from timing; no additional warmup. The same cluster
  retained data across runs, with distinct benchmark key prefixes.
- Three healthy runs came first. Then `node-e` received SIGTERM and exited;
  membership and quorum configuration stayed unchanged. The next three runs
  used only the four surviving nodes as client entry points.

The stopped-node case exercises connection refusal from replica calls. It does
not simulate a blackholed network or a slow replica. The node remained stopped
throughout those runs; restart convergence was not part of this experiment.

## Measurements

Each row is one independent run. Throughput counts successful GETs and PUTs
combined; percentiles are nearest-rank observations within that run. Per-method
percentiles describe the mixed workload, not separate GET-only or PUT-only runs.

| Condition | Run | Successful ops/s | Overall p95 (ms) | GET p95 (ms) | PUT p95 (ms) | Failed requests |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| healthy | 1 | 245.07 | 271.718 | 0.868 | 312.660 | 0 |
| healthy | 2 | 248.41 | 328.097 | 0.637 | 417.341 | 0 |
| healthy | 3 | 251.37 | 251.531 | 0.554 | 281.963 | 0 |
| node-e-stopped | 1 | 245.52 | 250.692 | 0.534 | 281.720 | 0 |
| node-e-stopped | 2 | 244.38 | 255.799 | 0.538 | 284.601 | 0 |
| node-e-stopped | 3 | 240.11 | 258.042 | 0.587 | 293.403 | 0 |

Median run throughput was **248.41 ops/s** with all nodes running
and **244.38 ops/s** with `node-e` stopped. This small,
sequential experiment establishes successful operation under this failure
condition; it does not establish a statistically significant performance change.
Writes were substantially slower than reads in these observations. No profiling
was performed to attribute that difference to a specific bottleneck.

[Raw JSON reports](local-2026-10-08.json) include every run, preparation results,
per-method throughput and latency, p50/p95/p99, errors, topology, runtime versions,
source hashes, and timestamps. Latency covers request construction through
response-body validation and closing. Closed-loop clients lower their offered
load while waiting, so these distributions do not represent fixed-rate arrivals
or correct for coordinated omission.

## Reproduce the workload

1. Build `./cmd/node` and `./cmd/bench` using `go build` without `-race`.
2. Start five native nodes using the IDs, ring settings, and quorums from
   `configs/cluster.local.json`. Give each node a new disposable persistent
   directory. Wait for all five `/health` endpoints to return 200.
3. Execute the following workload three times, saving each JSON report:

```bash
go run ./cmd/bench \
  -nodes http://127.0.0.1:8001,http://127.0.0.1:8002,http://127.0.0.1:8003,http://127.0.0.1:8004,http://127.0.0.1:8005 \
  -requests 5000 -concurrency 20 -read-percent 50 \
  -keys 1000 -value-bytes 256 -timeout 5s -format json \
  -description '5 native nodes; N=3 R=2 W=2; File.Sync persistence; healthy; record hardware and repetition'
```

4. Stop only the `node-e` process and wait for it to exit. Keep it in the shared
   membership file. Repeat the workload three times after removing port 8005
   from `-nodes` and updating the description to identify the stopped replica.
5. Stop the remaining experimental nodes and remove only their disposable data.

The saved run used temporary loopback ports, recorded in the JSON topology, to
avoid interfering with existing servers. Ports 8001–8005 above reproduce the
configuration on an otherwise free local cluster. Generated key prefixes differ
between runs, so exact key placement and timings will vary. `go run` compilation
occurs before the CLI's measured interval; an already-built executable avoids
that extra startup work.

The raw environment metadata identifies the base commit and hashes of the new
benchmark source. Key preloading, applications sharing the machine,
storage state, and run order should be recorded when comparing later results.
